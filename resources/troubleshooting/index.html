Troubleshooting Guide

Scenario 1: Can't Boot to Graphical Target​

Symptoms: System boots to command line instead of GUI, or fails to boot entirely.

Diagnosis:

systemctl get-default          # Check current target
systemctl list-units --failed  # Check for failed services
journalctl -xb                 # Check boot logs

Fix:

# Set default to graphical
sudo systemctl set-default graphical.target
# Or boot into it without rebooting
sudo systemctl isolate graphical.target

Exam tip: If you can't boot at all, edit GRUB at boot (press 'e'), add systemd.unit=rescue.target to the kernel line, boot, fix the issue, then reboot normally.

Scenario 2: Service Won't Start​

Symptoms: systemctl start httpd fails or service is inactive.

Diagnosis:

systemctl status httpd         # Check service status
journalctl -u httpd -n 50      # Check service logs
systemctl is-enabled httpd     # Check if enabled at boot

Common causes:

  • Package not installed → dnf install httpd
  • Port already in use → ss -tlnp | grep 80
  • SELinux blocking → getenforce, check /var/log/audit/audit.log
  • Config syntax error → httpd -t (configtest)

Fix:

# If SELinux is blocking
sudo setsebool -P httpd_can_network_connect on
sudo restorecon -Rv /var/www/html

# If config error
sudo httpd -t
# Fix the error, then:
sudo systemctl start httpd

Scenario 3: SELinux Blocking Access​

Symptoms: Permission denied even though file permissions look correct. Web server can't read files.

Diagnosis:

ls -Z /var/www/html/index.html    # Check SELinux context
getenforce                        # Check SELinux mode
sudo ausearch -m avc -ts recent   # Check for denials

Fix:

# Restore correct context
sudo restorecon -Rv /var/www/html

# Or set persistent context
sudo semanage fcontext -a -t httpd_sys_content_t "/var/www/html(/.*)?"
sudo restorecon -Rv /var/www/html

# If you need a boolean
sudo setsebool -P httpd_can_network_connect on

Exam tip: Never set SELinux to permissive or disabled on the exam. Fix the context or boolean instead.

Scenario 4: /etc/fstab Error on Boot​

Symptoms: System drops to emergency mode after reboot.

Diagnosis:

# In emergency mode, remount root as read-write
mount -o remount,rw /
# Check fstab
cat /etc/fstab

Fix:

# Comment out the bad line in /etc/fstab
sudo nano /etc/fstab
# Then reboot, or run:
sudo mount -a

Exam tip: Always test /etc/fstab with sudo mount -a before rebooting. If it errors, fix it first.

Scenario 5: Forgotten Root Password​

Symptoms: Can't log in as root.

Fix:

# Reboot and edit GRUB (press 'e' at boot menu)
# Add rd.break to the kernel line
# Press Ctrl+X to boot
# In the emergency shell:
mount -o remount,rw /sysroot
chroot /sysroot
passwd root
# Restore SELinux context
touch /sysroot/.autorelabel
exit
# System will reboot and relabel (takes time)

Scenario 6: Ansible Playbook Fails​

Symptoms: ansible-playbook returns errors.

Diagnosis:

# Run with verbose output
ansible-playbook -i inventory playbook.yml -vvv

# Run in check mode first
ansible-playbook -i inventory playbook.yml --check

# Syntax check
ansible-playbook -i inventory playbook.yml --syntax-check

# Test connectivity
ansible all -i inventory -m ping

Common causes:

  • SSH key not copied → ssh-copy-id
  • Inventory hostname wrong → Check inventory.ini
  • Module doesn't exist → Use FQCN (ansible.builtin.package)
  • Missing --become for root tasks
  • Vault password not provided → --ask-vault-pass

Exam tip: Run --syntax-check and --check before the full run. Fix syntax errors first.

Scenario 7: Can't Connect via SSH​

Symptoms: ssh user@host hangs or refuses connection.

Diagnosis:

# Check if SSH is running
sudo systemctl status sshd
# Check if port is open
sudo firewall-cmd --list-all | grep ssh
# Test with verbose output
ssh -vvv user@host

Fix:

# Enable SSH
sudo systemctl enable --now sshd
# Allow SSH in firewalld
sudo firewall-cmd --add-service=ssh --permanent
sudo firewall-cmd --reload
# Check SELinux isn't blocking
getenforce

Quiz​

Q1: You're in emergency mode after a bad /etc/fstab entry. What's the first command to run?

Answer: mount -o remount,rw / — in emergency mode, the root filesystem is read-only. Remount it read-write before editing fstab.

Q2: A web server can't serve files even though permissions are 755. What's the likely cause?

Answer: SELinux context. Check with ls -Z and fix with restorecon.

Challenge Checklist​

  • Boot into rescue.target via GRUB
  • Fix a broken /etc/fstab entry
  • Diagnose an SELinux denial with ausearch
  • Fix SELinux context with restorecon
  • Start a failed service and check its logs
  • Run ansible-playbook --syntax-check and --check
  • Recover a forgotten root password
  • Diagnose SSH connection failure
